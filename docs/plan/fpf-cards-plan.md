## Architecture Decision: Standalone crate, not embedded

**Context**: FPF card types (CSC, DRR, EFP) need to be shared across codegraph-rust, flowspec, reasoning-apps. Options:

1. **Embed in infer-core** — already has FPF constants (`TEMPORAL_STATE` etc)
2. **New standalone crate `fpf-cards`** — zero coupling, any consumer can depend
3. **Embed in haft** — haft already has FPF runtime (Go, wrong language)

**Decision**: Option 2 — standalone crate.

**Rationale**:
- infer-core is STABLE with semver contract — adding card types expands its surface unnecessarily
- Consumers (codegraph-rust, flowspec Python) shouldn't depend on the full infer stack
- haft is Go — can't share types across language boundary
- Standalone crate follows the same pattern as `pctl-core` (types only, no runtime)

**Consequences**:
- New crate to maintain (minimal — 3 structs, ~200 LOC)
- Consumers add `fpf-cards = { path = "../fpf-cards" }` or publish to crates.io later
- No circular dependencies possible

```
│   default = ["serde"]
│
├── src/
│   ├── lib.rs       # pub mod csc, drr, efp, error; re-export FpfCard trait
│   ├── error.rs     # CardError enum
│   ├── csc.rs       # CscCard { 5 fields } + validate()
│   ├── drr.rs       # DrrCard { context, decision, consequences, status } + validate()
│   └── efp.rs       # EfpCard { rendering_type, source_anchors, admissible_faces } + validate()
│
└── tests/
    └── validation.rs  # WF tests: valid cards pass, missing fields fail, edge cases
```

**Key design choices**:
- `serde` is optional feature (default on) — consumers without serialization needs skip it
- `thiserror` for ergonomic error types
- No `#[non_exhaustive]` on card structs — keep them simple, add fields in minor versions
- `FpfCard` trait has `validate()` and `card_type()` — consumers call `card.validate()?` before use
- All fields are `String` — no domain types, no enums for free-text fields. Only `DrrStatus` and `EfpType` are enums (closed sets from FPF spec)

**No platform/infra plan needed** — this is a library crate, no deployment, no CI beyond `cargo test`.
