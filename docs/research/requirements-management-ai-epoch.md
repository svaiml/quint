### #1 — Constructive Type-Theoretic RM

**Origin**: Per Martin-Löf (1972), Curry-Howard Isomorphism (1934/1969), dependent types in Agda/Idris/Lean/Coq

**AI-Epoch Fit Score**: 46/50

**Core Principle**: A requirement is a *type*. An implementation is a *term inhabiting that type*. Verification is type-checking. Under the Curry-Howard correspondence, propositions = types, proofs = programs. A requirement like "the system shall compute the balance of account A from all transactions T where T.account = A" becomes a dependent type whose inhabitants are programs — and non-implementation is a type error, not a missed deadline.

**Why It Matters NOW (2024–2030)**:
- LLMs writing code need machine-checkable contracts, not prose requirements. Types provide exactly this.
- Proof assistants (Lean 4, Rocq/Coq) are experiencing renaissance: LLM-assisted theorem proving (AlphaProof, 2024) brings formal verification into everyday engineering.
- EU AI Act requires runtime evidence of compliance; type-checked requirements produce that evidence automatically.
- "Typed Chain-of-Thought" (2025) extends Curry-Howard to LLM reasoning traces — every inference step is a typed logical inference, making AI reasoning itself auditable.
- axiomvm (ZomboCraftEco) implements this: deterministic sandboxed execution with proof-carrying execution traces is type-theoretic RM in practice.

**Limitation**: Requires significant upskilling. Full dependent type systems (Coq/Agda) have steep learning curves. Most industry teams operate at Haskell-level types at best. The LLM-to-formal-spec gap (LLMs achieve only 8.6% semantic correctness on TLA+ per 2025 benchmark) is still large.

### #2 — Formal RE + LLM Bridge (Neuro-Symbolic Hybrid)

**Origin**: Ferrari & Spoletini (2025), Information and Software Technology; nl2spec, SAT-LLM, Explanation-Refiner pipelines

**AI-Epoch Fit Score**: 44/50

**Core Principle**: A two-way roadmap: (1) LLMs translate ambiguous NL requirements into formal specifications; (2) formal methods provide guarantees of correctness, fairness, and trustworthiness for LLM-generated RE artifacts. Neither alone is sufficient — LLMs lack correctness guarantees; formal methods lack accessibility. The bridge uses prompt-only, few-shot, Chain-of-Thought, and neuro-symbolic pipelines (LLM + SMT solver) with iterative human-in-the-loop refinement.

**Why It Matters NOW (2024–2030)**:
- 58.2% of RE practitioners already use AI tools; 81.8% operate in Agile — the demand for formalizable Agile requirements is immediate.
- Iterative nl2spec pipelines (Chain-of-Thought + formal checker feedback loop) reduce ambiguity cycles by order of magnitude.
- REFSQ 2025 showed Knowledge Graph-assisted goal model construction using semantic similarity — this is the emerging infrastructure for the bridge.
- EU AI Act's August 2026 enforcement creates procurement demand for exactly this: NL requirements in (for product teams) + formally auditable proofs out (for regulators).

**Limitation**: Syntactic correctness ≠ semantic correctness. LLMs achieve 26.6% syntactic correctness on TLA+ but only 8.6% semantic correctness. The pipeline still requires significant HITL at the semantic verification stage. Code-specialized LLMs consistently underperform on formal languages relative to general LLMs — the expected specialization advantage does not materialize.

### #3 — Spec-Driven Development (SDD)

**Origin**: AWS Kiro (July 2025), GitHub Spec-Kit, Thoughtworks (2025); grounded in earlier API-contract-first and PRD-first approaches

**AI-Epoch Fit Score**: 43/50

**Core Principle**: The specification is the *source of truth*; code is a derived artifact. Specs define external behavior (input/output mappings, preconditions, postconditions, invariants, interface types, integration contracts, state machines) — not implementation details. AI agents execute against specs as "super-prompts" that eliminate ambiguity and reduce error rates by up to 50%. The four-stage canonical workflow: Specification → Technical Plan → Tasks → Implementation.

**Why It Matters NOW (2024–2030)**:
- Directly addresses the "vibe coding" failure mode: AI generates code that works once but is unmaintainable because requirements were never formalized.
- Specs integrated with CI/CD pipelines catch requirement-code divergence immediately (traditional docs drift silently).
- SDD is rapidly becoming the industry standard response to agentic coding: Amazon Kiro, GitHub Spec-Kit, Anthropic's Claude Code workflows all implement variants of this approach.
- FlowSpec-Forge IS an implementation of SDD: `/flow:specify` creates PRDs as specs; `/flow:plan` + `/flow:implement` derive code from specs; `/flow:validate` checks spec-code conformance.

**Limitation**: SDD specs are behavioral but not yet formally verifiable in most implementations. The gap between "machine-readable spec" and "mechanically checkable proof" requires bridging to Type-Theoretic RM (#1) or Formal RE (#2). Without that bridge, SDD reduces requirement drift but does not eliminate it.

### #4 — EARS + 4-Valued Logic (Belnap-Augmented Structured NL)

**Origin**: EARS: Alistair Mavin, Rolls-Royce (2009); 4-Valued Logic: Nuel Belnap (1977); integration: emerging in ZomboCraftEco

**AI-Epoch Fit Score**: 40/50

**Core Principle**: EARS provides five structured NL templates for requirements (Ubiquitous, Event-Driven, State-Driven, Conditional, Optional Feature) that eliminate ambiguity while remaining human-writable. The canonical form `While <precondition>, When <trigger>, the <system> shall <response>` is parseable by NLP and LLM agents with high reliability. Augmenting EARS with Belnap's four-valued logic (TRUE/FALSE/UNKNOWN/BOTH) closes the incompleteness problem: requirements can have truth value UNKNOWN (not yet decided) or BOTH (conflicting stakeholder inputs) without collapsing into classical two-valued inconsistency.

**Why It Matters NOW (2024–2030)**:
- GitHub Spec-Kit's issue tracker already lists EARS integration as a feature request (#1356) — industry is moving.
- EARS is used by Airbus, NASA, Siemens, Honeywell, Intel — industrial-grade adoption with proven AI-parsability.
- Requirements in early phases are genuinely four-valued: stakeholders say contradictory things (BOTH); some requirements are not yet gathered (UNKNOWN). Two-valued classical logic forces premature closure. Belnap logic allows incremental formalization.
- zz-notation implements this: the four truth values (true/false/unknown/paradox) map exactly to Belnap's FIRST/LAST/NONE/BOTH.

**Limitation**: EARS templates cover only functional/behavioral requirements well. NFRs (performance, security, fairness) require additional layers. The four-valued logic extension is not yet standardized — zz-notation is the closest formal proposal but remains ZomboCraftEco-internal.

### #5 — Goal-Oriented RE (KAOS / i* / GORE)

**Origin**: KAOS: van Lamsweerde (UCLouvain, 1993); i*: Eric Yu (Toronto, 1994); NFR Framework: Lawrence Chung (UT Dallas, 1992)

**AI-Epoch Fit Score**: 39/50

**Core Principle**: Requirements are *goals* in a hierarchical refinement tree, not flat feature lists. KAOS decomposes system goals into sub-goals, with obstacle analysis that formally identifies conditions threatening goal achievement. i* models strategic actors and their intentional relationships (dependencies, commitments, softgoals). The NFR Framework handles non-functional requirements as *softgoals* with operationalizing refinements and contribution links. Goals have agents responsible for them; obstacles have countermeasures; the entire structure is a formal directed graph amenable to automated reasoning.

**Why It Matters NOW (2024–2030)**:
- Knowledge Graph-assisted goal model construction (REFSQ 2025) enables LLM-assisted i* modeling using semantic similarity and NLI.
- Goal graphs are naturally agent-assignable: each sub-goal can be dispatched to an AI agent, with KAOS's obstacle analysis providing automatic risk detection.
- infer's DETECT verb implements obstacle monitoring: `detect violation(goal_precondition)` is goal obstacle detection.
- infer's STRESS verb implements KAOS sensitivity analysis: identify which facts, if changed, would falsify a goal derivation.
- Aligns with FlowSpec's DVF+V scoring in `/flow:assess` — Desirability/Viability/Feasibility/Validity map to KAOS goal categories.

**Limitation**: KAOS and i* tooling is academically maintained (Objectiver, jUCMNav) and has not achieved widespread industrial adoption. Most AI coding pipelines do not natively ingest KAOS goal models — the bridge from goal model to implementable spec requires additional infrastructure. i* softgoal refinement remains under-automated.

### #6 — BDD / Gherkin + LLM Orchestration

**Origin**: Dan North (2006); Cucumber framework; augmented by LLM orchestration 2023–2025

**AI-Epoch Fit Score**: 37/50

**Core Principle**: Requirements are expressed as *executable scenarios* in Given/When/Then (Gherkin) syntax. Scenarios are simultaneously human-readable acceptance criteria and machine-executable tests. LLMs now generate Gherkin from user stories using zero-shot, few-shot, and Chain-of-Thought prompting (ICAART 2025). Agentic AI closes the loop: agent reads Gherkin → generates code → runs Cucumber → feeds failures back → refines implementation.

**Why It Matters NOW (2024–2030)**:
- LLMs excel at Gherkin generation: structured syntax + examples = natural few-shot target.
- BDD is resurging specifically because Gherkin is LLM-friendly: "LLMs thrive on structure, checklists, and concrete examples" (Humanizing Work, 2025).
- Hardware verification applications: LLM-based BDD for hardware design reduces manual workload while increasing coverage (arXiv 2512.17814, 2025).
- EU AI Act's requirement for operational evidence (not declarations) maps directly to BDD's executable test artifacts.

**Limitation**: BDD at scale produces scenario proliferation — thousands of Gherkin scenarios become unmaintainable. BDD tests functional behavior but not non-functional requirements (latency, security, fairness). Gherkin is not formally verifiable (it is test-based, not proof-based) — a test suite can pass and still contain logical contradictions in requirements. This is the gap that criterium's L2/L3 assurance tiers close.

### #7 — MBSE / SysML v2

**Origin**: INCOSE MBSE initiative (2002); SysML (OMG, 2003); SysML v2 (OMG, March 2025)

**AI-Epoch Fit Score**: 37/50

**Core Principle**: Requirements are embedded in a unified system model (SysML block definition diagrams, use cases, activity diagrams, parametric diagrams) rather than living in separate documents. MBSE ensures requirements trace to design elements, which trace to verification artifacts, which trace to test results — creating an unbroken chain of traceability across the system lifecycle. SysML v2 (2025) adds: improved precision, native textual syntax (KerML), formal semantics, and better interoperability.

**Why It Matters NOW (2024–2030)**:
- IBM's Engineering AI Hub 1.1 (2024) introduces MBSE use-case discovery agents that interpret NL requirements and create SysML model elements automatically.
- SysML v2's formal textual syntax (KerML) is machine-readable in a way SysML v1's diagram-centric approach was not — enabling AI agent consumption.
- Regulated industries (aerospace, defense, medical devices) are mandating MBSE as procurement requirement.
- AI-Assisted MBSE with SysML textbook (2024, Rosenberg/Weilkiens/Moberley) marks MBSE's crossing into AI-augmented practice.

**Limitation**: MBSE tooling (Rhapsody, Cameo, Capella) is enterprise-grade proprietary and expensive. SysML v2 is new (March 2025) — tooling ecosystem is immature. AI-generated SysML models lack structural rigor and traceability required for direct implementation — the LLM-to-SysML quality gap is significant. Not suited to fast-moving product teams.

### Deep Foundations: Which School Actually Wins

**Constructive Type Theory (Martin-Löf / Curry-Howard) is the deepest foundation for AI-epoch RM.**

Rationale:
- Under Curry-Howard, a requirement statement *is* a type. An implementation *is* a proof term inhabiting that type. Verification *is* type-checking. This is not a metaphor — it is an identity. The gap between "requirement" and "verified implementation" collapses.
- Dependent types extend this to full-power specifications: a type can say "a list of length n" or "a function whose output satisfies predicate P on its input" — these are requirements in the richest sense.
- This is why **axiomvm** is the deepest IP in the ZomboCraftEco stack: deterministic sandboxed execution with proof-carrying traces IS constructive type theory applied to runtime verification.
- The 2025 "Typed Chain-of-Thought" framework (arXiv 2510.01069) extends Curry-Howard to LLM reasoning: each inference step is a typed logical inference, and a faithful reasoning trace is a well-typed program. This means LLM reasoning can be formally audited — which is the core EU AI Act compliance requirement.

**Second foundation: Belnap's 4-valued logic (Paraconsistent Logic).**

Rationale:
- Classical two-valued logic collapses under incomplete/contradictory stakeholder information — the most common real condition in requirements elicitation.
- Belnap's bilattice (TRUE/FALSE/UNKNOWN/BOTH) handles partial information without explosion. UNKNOWN requirements can co-exist with TRUE/FALSE requirements; BOTH (contradictory) requirements can be isolated without contaminating the rest of the specification.
- zz-notation operationalizes this. The recent finding that Belnap logic has four distinct imprints in computer science (linear logic via Chu construction, domain theory via d-frames, blame calculus, LVars for distributed programming) confirms this is not academic curiosity — it is load-bearing infrastructure for distributed, incomplete, real-world information systems.
- The Bilattice-Catastrophe Isomorphism (arXiv 2604.07690, 2026) establishes formal connections between four-valued logic and catastrophe theory, suggesting zz-notation's semantics will gain further theoretical grounding.

**Third foundation: Orthodox Apophatic Method (via TheoSciTech lens).**

Rationale:
- The apophatic tradition (what-it-is-NOT before what-it-IS) maps to requirements as constraint elimination: before specifying what the system shall do, eliminate what it must not, cannot, or need not do.
- This maps to infer's STRESS verb (what facts, if changed, would falsify a derivation?) and to pctl-rs's trust/freshness decay modeling (what do we NOT know with confidence?).
- Kolmogorov complexity provides the information-theoretic grounding: the minimal description of a requirement set is the irreducible constraint kernel — what cannot be removed without changing the specification. Requirements quality = minimal Kolmogorov complexity of the specification. FlowSpec's DVF+V scoring is an approximation of this: assessing which requirements carry irreducible information.
